How it links together.

The wiring, in three phases.

— same fourteen services, three different time horizons —

Trace one push, beat by beat.

▸ T+0 → T+~3min

— from git push on a laptop to a returning visitor seeing the new build, with a label on every wire —

01 T+0 Local build

Vite / Astro compiles your source on the laptop. ESM modules bundle to dist/. No network yet.

your laptop · Node · ~3–10s
02 T+~5s Push to origin

git push origin main uploads the diff over SSH. GitHub stores the commit, advances the branch ref, and writes a delivery record for every webhook subscriber.

SSH/22 or HTTPS · payload < 1 MB
03 T+~7s Webhook fan-out

GitHub fires POST /hooks/github with a JSON push event to every connected service. Netlify and Railway both receive it within a second of each other.

HTTPS · signed (X-Hub-Signature-256)
04 T+~10s Build runners spin up

Netlify boots a fresh Linux container, clones the repo at the new SHA, runs npm ci && npm run build. Railway does the equivalent against your Dockerfile or buildpack.

ephemeral container · network in, no persistent disk
05 T+~90s Frontend publishes

Netlify uploads the new dist/ to its global CDN, atomically swaps the alias for yoursite.com, and purges the edge cache. The next request anywhere in the world serves the new HTML.

atomic deploy · zero-downtime
06 T+~3min API rolls over

Railway boots the new container alongside the old, runs the health check, then drains the old one. api.yoursite.com is now serving the new code — without dropping in-flight requests.

rolling deploy · health-checked cutover
07 first visit Browser asks for the host

A user types yoursite.com. Their resolver walks the DNS chain — root, .com, your NS records (Cloudflare), final A/AAAA. Cached for the TTL after that.

UDP/53 · ~10–80ms cold, <1ms warm
08 +~30ms TLS at the edge

Browser opens TCP, then TLS, with the nearest Cloudflare PoP. Cloudflare presents the cert it minted for your domain — you never touched a private key.

TCP/443 · TLS 1.3 · 1-RTT handshake
09 +~50ms HTML is returned

Cache hit at the edge → response in tens of ms. Cache miss → Cloudflare proxies to Netlify origin, gets the HTML, fills the cache for next time. Either way the user has bytes.

HTTPS · gzip/br · cached unless busted
10 +~100ms JS hydrates

The browser parses the HTML, fetches the JS bundle (cached the same way), and runs it. The Firebase Web SDK opens a WebSocket. The Umami snippet fires its first beacon.

parallel fetches · HTTP/2 multiplex
11 +~200ms App calls the API

The hydrated app does fetch('https://api.yoursite.com/me'). CORS preflight if the headers warrant it, then the real request. Cloudflare proxies it through to Railway.

HTTPS · JSON · CORS-checked
12 +~250ms API talks to Firebase

The Railway service uses the Firebase Admin SDK with its service-account key (env var) to verify the user's ID token, read their record, and return JSON.

gRPC · ~30–60ms · Google's network
13 +~300ms Side effects fire async

If the request triggers an email (signup, reset), the API hits POST resend.com/emails — not blocking the response. The user sees their page; mail goes out in the background.

HTTPS · async · retried on Resend's side
14 +continuous Realtime sync runs

The Firebase WebSocket from step 10 is now pushing live updates to the page — new messages, presence, whatever the app subscribed to. No polling, no extra fetches.

WSS/443 · long-lived · auto-reconnect
15 out-of-band Googlebot crawls

Independently of any user, Googlebot fetches /sitemap.xml, walks the URLs, and reports back to Search Console — which surfaces it in the dashboard hours or days later.

HTTPS · scheduled · async to your traffic

Four scenarios, one wiring.

▸ SAME BOX, DIFFERENT WIRES

— the same fourteen services, four different paths through them —

scenario · 01

You ship a typo fix

Single-line change. Push, wait three minutes, refresh.

  1. Laptop→GitHubgit push
  2. GitHub→Netlifywebhook · build
  3. Netlify→Cloudflarecache purged on swap
  4. User refreshes→edgenew HTML, no API call needed

Railway, Firebase, Resend, Umami untouched. Pure static path.

scenario · 02

A first-time visitor lands

Cold cache, never been here, no account.

  1. Browser→DNSresolve via Cloudflare NS
  2. Browser→CloudflareTLS 1.3 handshake
  3. Cloudflare→Netlify origincache miss · fetch HTML
  4. Browser→Umamibeacon · pageview

No API calls, no DB. Static HTML + analytics ping. Sub-second.

scenario · 03

A user signs up

Form submit. Account created. Welcome email lands.

  1. Frontend→Firebase AuthWeb SDK · createUser
  2. Frontend→API · RailwayPOST /signup · ID token
  3. API→Firebase DBAdmin SDK · write profile
  4. API→ResendPOST /emails · async
  5. Resend→User inboxSMTP · ~10s

All four side-services touched. Hot path stays under 400ms; mail is fire-and-forget.

scenario · 04 · failure

Cloudflare is down

A real outage. What survives, what doesn't.

  1. Browser→DNSSERVFAIL · NS unreachable
  2. All requests→timeoutno resolver, no TLS, no anything
  3. Direct→netlify.app subdomainstill works · bypasses CF
  4. Mitigation→DNS-only modegrey-cloud the records, skip CF proxy

Putting one vendor on the hot path = single point of failure. Worth knowing the workaround before the day arrives.

When a link breaks.

▸ SYMPTOM · LOOK · TEST

— each critical handoff, what it looks like when it fails, and the first place to check —

// link 01 · NS delegation

Porkbun → Cloudflare

Symptom: domain doesn't resolve anywhere. dig yoursite.com returns SERVFAIL or the wrong IP.

Look: Porkbun → Domains → NS records. Should be *.ns.cloudflare.com. Newly-set NS can take 24h to propagate.

Test: dig NS yoursite.com from the terminal. Should match what Cloudflare gave you.

// link 02 · CNAME

Cloudflare → Netlify

Symptom: domain resolves, but the page is a Netlify "site not found" or a 404 from Cloudflare.

Look: Cloudflare DNS panel — root or www CNAME pointing at your-site.netlify.app. Also check Netlify → Domain Management — the custom domain must be added there too.

Test: curl -I https://yoursite.com — the response headers should mention Netlify.

// link 03 · webhook

GitHub → Netlify build

Symptom: push lands, no build kicks off. Site stays on the old version.

Look: GitHub → repo Settings → Webhooks → the Netlify hook. Recent deliveries should be 2xx. If they're red, click for the error body.

Test: Re-deliver the last push from the GitHub webhook page; watch Netlify's deploys feed light up.

// link 04 · build

Netlify / Railway build

Symptom: deploy started, then failed. Old site still serving (good!), but new code never lands.

Look: Netlify deploy log or Railway build log — the failing line is almost always npm ci, a missing env var, or a typo in the build command.

Test: Reproduce locally with the same Node version: nvm use 20 && npm ci && npm run build.

// link 05 · CORS

Frontend → API

Symptom: calls fail in the browser, work in curl. Console shows "blocked by CORS policy".

Look: API response headers — Access-Control-Allow-Origin must include https://yoursite.com. Preflight (OPTIONS) must return 204.

Test: curl -I -H "Origin: https://yoursite.com" https://api.yoursite.com/me — inspect the headers.

// link 06 · auth

API → Firebase

Symptom: API returns 401 or 500 with "invalid credentials" / "permission denied". Frontend logs in fine.

Look: Railway env — FIREBASE_SERVICE_ACCOUNT JSON must be valid, the project ID must match the frontend's. Firebase → Project Settings → Service Accounts to regenerate.

Test: in a Railway shell, log in with the Admin SDK and call auth().listUsers(1).

// link 07 · email

API → Resend

Symptom: signup succeeds, no welcome email arrives. No error, just silence.

Look: Resend dashboard → Emails — look for the message. Check status: queued, delivered, bounced, marked spam. Verify the sender domain has DKIM/SPF green.

Test: curl -X POST https://api.resend.com/emails ... with the API key — if it fails outside your app, it's not your app.

// link 08 · WebSocket

Frontend → Firebase realtime

Symptom: page loads, but live updates never come. No errors; just stale data.

Look: browser DevTools → Network → WS tab. Look for a long-lived wss://*.firebaseio.com connection. Status should be 101 / open. Firebase → Realtime DB → Rules: a deny rule will silently drop reads.

Test: swap a value in the Firebase console; the open page should update within 1s.

// link 09 · analytics

Frontend → Umami

Symptom: dashboard shows zero visits. Site is clearly being viewed.

Look: DevTools → Network — filter by send. Should see a 200 to /api/send. Ad-blockers commonly nuke the request — check from a clean profile.

Test: visit the site in a private window with no extensions; check Umami within ~10s.

// link 10 · indexing

Googlebot → Search Console

Symptom: "0 valid pages" or new pages never show up in search.

Look: Search Console → Indexing → Pages. Filter for "not indexed" reasons. Often: noindex meta tag, robots.txt blocking, or simply too new.

Test: Search Console → URL Inspection → "Test live URL" gives a real-time fetch and the exact reason.

// rule of thumb

If something is broken, walk the wires in order: DNS first, then TLS, then origin, then API, then DB, then external services. Two minutes of dig + curl -I + a glance at the build log resolves nine out of ten incidents before you even open a dashboard.
